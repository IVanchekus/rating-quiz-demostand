# Питерский мостик IT Challenge

**Техническое описание проекта и архитектура (версия 1.0)**  
**Дата:** 19 октября 2026 года  
**Статус:** спецификация для реализации MVP

## 1. Общая идея и цель

«Питерский мостик IT Challenge» — интерактивная викторина для мероприятий компании «Питерский мостик», объединяющей четыре компании: **Связьком, Sensory Hub, Систематикс и Galaxy**. Посетитель сканирует QR-код на стойке, переходит в Telegram-бота и присоединяется к активной игровой комнате. В боте он последовательно проходит **10 индивидуально подобранных вопросов** с вариантами ответа. За правильный ответ получает баллы в зависимости от скорости. После единственного ответа бот показывает правильный вариант и краткое объяснение, а следующий вопрос открывается только кнопкой **«Далее»**.

Отдельный веб-сайт показывает **публичный рейтинг всех участников конкретной комнаты**, обновляя данные обычными HTTP-запросами **каждые 15 секунд**, без WebSocket. Место в рейтинге **никогда не показывается в Telegram-боте** — только на сайте.

Цель игры — заинтересовать посетителей деятельностью компаний и IT, побудить их общаться с представителями стенда и добавить соревновательный элемент.

## 2. Состав системы и технологический стек

| Компонент | Технология | Назначение |
|---|---|---|
| Telegram-бот | Python 3.12+, `python-telegram-bot` | Регистрация, вопрос/ответ, обратная связь, кнопка «Далее» |
| Backend | Python 3.12+, FastAPI | Единая игровая логика, REST API, начисление баллов |
| ORM и миграции | SQLAlchemy 2.x, Alembic | Доступ к базе и управление схемой |
| СУБД | **MySQL 8.x**, InnoDB | Пользователи, комнаты, вопросы, прогресс, ответы |
| Веб-сайт | Vue 3 + Vite | Публичный рейтинг, страница комнаты, опционально администрирование |
| Обновление сайта | HTTP polling через `fetch` | Запрос рейтинга каждые **15 секунд** |
| Развёртывание | Docker Compose | Отдельные процессы API, bot, worker, MySQL, frontend |
| Конфигурация | `.env` | Секреты и значения по умолчанию |

Backend и бот используют **общий слой сервисов** и одну БД. Бот не обязан обращаться к API по HTTP внутри системы: его обработчики могут напрямую вызывать те же Python-сервисы. Сайт работает с Backend через REST. WebSocket, Redis и отдельные микросервисы для MVP не нужны.

```text
Telegram-клиент -> Telegram Bot API -> Python Bot handlers --┐
                                                             ├-> Game Services -> MySQL
Браузер -> Vue 3 -> HTTP GET /api/... -> FastAPI ------------┘
                                  (каждые 15 секунд)
Worker (таймеры и завершение комнат) -> Game Services -> MySQL
```

## 3. Основные бизнес-правила

1. **Одна регистрация на комнату:** для пары `(room_id, telegram_user_id)` допускается только одно участие; перезапуск `/start`, удаление диалога или повторное сканирование QR не сбрасывают прогресс. В *другой* комнате тот же Telegram-пользователь может участвовать снова.
2. **Один ответ на вопрос:** первый принятый сервером вариант окончателен. Пересдать вопрос, выбрать другой вариант или получить дополнительные баллы нельзя.
3. **Индивидуальный набор:** при регистрации каждому участнику один раз назначаются 10 различных вопросов из разрешённого для комнаты банка. Порядок фиксируется. **Внутри набора повторов нет**; между разными участниками вопросы могут пересекаться, а наборы или порядок могут отличаться.
4. **Последовательная выдача:** одновременно доступен не более один вопрос участника. Следующий отправляется **только после нажатия «Далее»** по завершении предыдущего.
5. **Форма ответа:** текст вопроса + 2 или более варианта в виде Telegram inline-кнопок; у вопроса ровно один правильный вариант.
6. **Отображение результата:** после ответа в исходном Telegram-сообщении заменяются варианты ответа на результат, **правильный вариант**, обязательное **краткое объяснение правильности** и кнопку «Далее». Сам вопрос можно оставить в тексте; удаляется интерактивная клавиатура ответов, а не запись вопроса в БД.
7. **Таймер:** у каждого вопроса свой срок ответа. Время хранится и проверяется на сервере. Просроченный вопрос получает 0 баллов, раскрывает верный вариант с пояснением и допускает переход «Далее», пока комната активна.
8. **Баллы:** максимум 100 за вопрос по умолчанию; скорость влияет на количество баллов только при правильном ответе. Максимум за 10 вопросов — 1000 баллов при настройках по умолчанию.
9. **Рейтинг:** общий для комнаты; виден **только на сайте**. В боте разрешено показать *личные баллы* и прогресс, но **не место/позицию в рейтинге**.
10. **Время комнаты:** комнату открывает организатор; участвовать и отвечать можно до `ends_at`. После завершения комнаты ответы не принимаются, незавершённые задания закрываются, баллы фиксируются.
11. **Объяснение обязательно:** нельзя опубликовать вопрос без объяснения, вариантов и ровно одного правильного варианта.
12. **Предотвращение изменения истории:** вопросы и варианты, уже используемые в действующей комнате, не должны изменяться так, чтобы это меняло результаты; применять версионирование/копирование редакций или блокировку редактирования.

> **Уточнение о случайности:** персональные наборы **различаются за счёт случайной выборки/порядка**, но требование гарантировать уникальный набор для каждого человека не устанавливается. Если такая гарантия понадобится, потребуется отдельный алгоритм распределения и достаточно большой банк.

## 4. Пользовательские сценарии Telegram-бота

### 4.1 Вход по QR-коду

1. Организатор создаёт и запускает комнату, например «День партнёров — 19.10».
2. Система создаёт непрогнозируемый `join_code` и ссылку вида `https://t.me/YourQuizBot?start=room_ABCD1234`.
3. QR-код ведёт на ссылку. Пользователь нажимает Start.
4. Бот идентифицирует Telegram пользователя по **числовому `telegram_id`**; `username` может отсутствовать или меняться.
5. Проверяется доступность комнаты (`status = active`, текущее время до `ends_at`).
6. При первом входе в транзакции создаются `participants` и ровно N записей `participant_questions` с уникальными вопросами и `position` от 1 до N.
7. При повторном входе новая регистрация и новая выдача вопросов **не происходят**. Бот восстанавливает текущее состояние: ожидающий вопрос, уже полученный результат с «Далее» или финальное сообщение.
8. Бот показывает приветствие, правила и первый вопрос (либо кнопку «Начать», если организаторы решат добавить этот предварительный экран).

**Тексты ошибок:** «Комната ещё не началась», «Комната завершена», «Вы уже завершили прохождение», «Не удалось подготовить вопросы; обратитесь к организатору».

### 4.2 Экран вопроса (Telegram)

```text
Вопрос 3 из 10                           Осталось: до 30 секунд

Какой HTTP-метод предназначен для частичного обновления ресурса?

[ GET ]
[ POST ]
[ PATCH ]
[ DELETE ]
```

На самом Telegram-сообщении доступны inline-кнопки с короткими данными callback, например `answer:<participant_question_id>:<option_id>`; использовать `callback_query.from_user.id` для авторизации. Не доверять присланному идентификатору пользователя, флагу правильности или баллам из callback. Ограничение Telegram на `callback_data` — 64 байта.

### 4.3 После ответа

```text
Вопрос 3 из 10
Какой HTTP-метод предназначен для частичного обновления ресурса?

❌ Неправильный ответ
Ваш выбор: POST
Правильный ответ: PATCH

Почему это правильно: PATCH позволяет отправлять набор частичных
изменений ресурса, а не заменять всё его представление.

Получено: 0 из 100 баллов

[ Далее → ]
```

Для правильного ответа показывается `✅ Правильно`, выбранный вариант, правильный ответ, такое же объяснение и начисленные баллы. Для просроченного — `⌛ Время вышло`, правильный вариант, объяснение и 0 баллов. **Попытаться ответить снова нельзя.**

После получения результата бот редактирует существующее сообщение через `editMessageText`/`editMessageReplyMarkup`, убирает старые варианты и добавляет одну кнопку «Далее». Если редактирование невозможно, отправляет новое сообщение с сохранённым результатом, **не перерассчитывая** баллы.

### 4.4 Кнопка «Далее»

1. Бот получает `next:<participant_question_id>`.
2. Проверяет владельца, комнату и статус текущего вопроса (`answered` или `expired`).
3. Под блокировкой состояния участника убеждается, что следующего активного вопроса ещё нет.
4. Находит следующий назначенный вопрос по `position` и отправляет его, активируя его таймер при успешной выдаче.
5. Двойное нажатие «Далее» не открывает два вопроса и не пропускает очередной.
6. После десятого вопроса участие получает статус `completed`.

**Важное поведение:** если пользователь не нажимает «Далее», таймер следующего вопроса ещё не идёт; общая комната при этом продолжает отсчитывать своё время.

### 4.5 Завершение в боте

```text
🎉 Игра завершена!
Вы ответили на 10 вопросов.

Ваш результат: 780 из 1000 баллов.
Спасибо за участие! Итоговый рейтинг смотрите на экране мероприятия.
```

**Не выводить** `#4`, «4-е место», список лидеров, номер позиции либо API-ссылку с персональной позицией в сообщениях Telegram. Команда `/score` показывает только собственные баллы и прогресс.

### 4.6 Команды

| Команда | Назначение |
|---|---|
| `/start room_CODE` | Войти в комнату / восстановить своё участие |
| `/start` | Показать текущее состояние и инструкцию (если комнаты ещё нет — попросить QR-ссылку) |
| `/score` | Показать собственные баллы и число пройденных вопросов, **без места** |
| `/help` | Правила игры |

## 5. Таймер и формула баллов

Параметры по умолчанию: 30 секунд на обычный вопрос, максимум 100 баллов, 0 за неверный ответ или истечение таймера.

**Вариант формулы MVP — линейное снижение:**

```python
if not is_correct or is_expired:
    points = 0
else:
    elapsed_ms = max(0, answered_at_ms - sent_at_ms)
    limit_ms = question_time_limit_seconds * 1000
    points = max(min_correct_points,
                 round(max_points_per_question * (1 - elapsed_ms / limit_ms)))
    points = min(points, max_points_per_question)
```

Пример при 30 секундах и 100 максимальных баллах: 0 сек → 100, 6 сек → 80, 15 сек → 50, 30 сек/позже → 0. **Граница срока:** ответы принимаются только если серверное время строго меньше `expires_at`.

Для **интерактивных вопросов**, требующих общения со стендистом, разрешён отдельный `time_limit_seconds`, например 120–300 секунд. При желании их оценку можно рассчитывать по другой политике; в MVP используется единая формула.

**Особенность Telegram:** абсолютная точность «с момента отображения на устройстве пользователя» недостижима. Практическое правило MVP — фиксировать `sent_at` и `expires_at` после подтверждения успешной отправки сообщения через Bot API. Таймер визуально показывается текстом, но в Telegram-сообщении не обновляется каждую секунду; проверяется на сервере.

## 6. Сайт

### 6.1 Публичная страница рейтинга

URL, например `/rooms/<public_code>` или `/leaderboard/<room_id>`.

Элементы страницы:

- Заголовок «Питерский мостик IT Challenge», название комнаты, статус (ожидает/идёт/завершена).
- Время до конца комнаты (можно отсчитывать локально от серверного `ends_at`; данные периодически синхронизируются).
- Общее число зарегистрированных участников.
- Сортируемый сервером список: **место, отображаемое имя/Telegram username, сумма баллов, число закрытых вопросов**.
- Удобная компоновка для телевизора/проектора: крупные цифры, первые 3 места выделены, полный список при необходимости прокручивается.
- Завершённый рейтинг доступен для просмотра после закрытия комнаты.

Если `username` отсутствует, показывать безопасный fallback: Telegram `first_name` либо нейтральное `Участник 123`. Не показывать числовой Telegram ID публично. При одинаковом `username` различать участников по внутреннему идентификатору, не считая `username` уникальным.

### 6.2 Обновление каждые 15 секунд

- Первое `GET` сразу при открытии страницы.
- Далее `GET /api/rooms/{id}/leaderboard` раз в **15 секунд**.
- Не создавать наложенных запросов, если предыдущий ещё выполняется (например, рекурсивный `setTimeout` после завершения).
- При ошибке сети оставить предыдущий рейтинг и показать ненавязчивый статус обновления.
- После завершения комнаты можно прекратить polling (или выполнять его реже, если финализация ещё идёт).
- **WebSocket не использовать.**

### 6.3 Администратор (рекомендуемый MVP-функционал)

Авторизованная административная панель позволяет создать/завершить комнату, выбрать вопросы или категории, задать лимиты, просмотреть QR-код, добавить/редактировать вопросы с вариантами и объяснением. Секретные административные endpoints должны быть закрыты авторизацией; публичный рейтинг остаётся доступным без входа.

## 7. База данных MySQL: 9 таблиц

**Договорённости:** MySQL 8.x, InnoDB, `utf8mb4`, PK — `BIGINT UNSIGNED AUTO_INCREMENT` (кроме естественных уникальных ключей). Время в UTC, тип `DATETIME(3)`. `FK` означает внешний ключ. Поля `created_at`/`updated_at` заполняются приложением или соответствующими DEFAULT/ON UPDATE.

### 7.1 `users`

| Поле | Тип | Ограничения / назначение |
|---|---|---|
| `id` | BIGINT UNSIGNED | PK |
| `telegram_id` | BIGINT | NOT NULL, UNIQUE; реальный идентификатор Telegram |
| `username` | VARCHAR(32) | NULL, отображаемый username |
| `first_name` | VARCHAR(255) | NOT NULL |
| `last_name` | VARCHAR(255) | NULL |
| `created_at` | DATETIME(3) | NOT NULL |
| `updated_at` | DATETIME(3) | NOT NULL |

`username` **не является** идентификатором и не должен иметь UNIQUE. Уникальность Telegram ID ограничивает число участий *с одного аккаунта*, но не может доказать, что физический человек не использует два аккаунта.

### 7.2 `rooms`

| Поле | Тип | Ограничения / назначение |
|---|---|---|
| `id` | BIGINT UNSIGNED | PK |
| `title` | VARCHAR(255) | NOT NULL |
| `join_code` | VARCHAR(64) | NOT NULL, UNIQUE; для QR-deep-link |
| `status` | ENUM('draft','active','finished','cancelled') | NOT NULL, DEFAULT 'draft' |
| `starts_at` | DATETIME(3) | NULL до запуска |
| `ends_at` | DATETIME(3) | NULL до запуска |
| `duration_minutes` | INT UNSIGNED | NOT NULL, DEFAULT 60 |
| `questions_count` | SMALLINT UNSIGNED | NOT NULL, DEFAULT 10 |
| `question_time_limit_seconds` | INT UNSIGNED | NOT NULL, DEFAULT 30 |
| `max_points_per_question` | SMALLINT UNSIGNED | NOT NULL, DEFAULT 100 |
| `min_correct_points` | SMALLINT UNSIGNED | NOT NULL, DEFAULT 0 |
| `created_at` | DATETIME(3) | NOT NULL |
| `updated_at` | DATETIME(3) | NOT NULL |

Сервер проверяет `starts_at <= now < ends_at` и `status='active'`. Настройки фиксируются при запуске комнаты; изменение во время игры запрещено либо требует явно предусмотренной процедуры.

### 7.3 `categories`

Категории — **отдельная таблица**, без ENUM в `questions`.

| Поле | Тип | Ограничения / назначение |
|---|---|---|
| `id` | BIGINT UNSIGNED | PK |
| `name` | VARCHAR(100) | NOT NULL |
| `slug` | VARCHAR(100) | NOT NULL, UNIQUE |
| `description` | TEXT | NULL |
| `is_active` | BOOLEAN | NOT NULL, DEFAULT TRUE |
| `created_at` | DATETIME(3) | NOT NULL |
| `updated_at` | DATETIME(3) | NOT NULL |

Начальные категории: `programming` (Программирование), `company` (О компании), `interactive` (Интерактивные задания), `technology` (IT и технологии). Новые категории создаются без миграции схемы.

### 7.4 `questions`

| Поле | Тип | Ограничения / назначение |
|---|---|---|
| `id` | BIGINT UNSIGNED | PK |
| `category_id` | BIGINT UNSIGNED | NOT NULL, FK → categories.id |
| `text` | TEXT | NOT NULL, вопрос |
| `explanation` | TEXT | **NOT NULL**, краткое объяснение, не пустая строка по валидации |
| `company` | ENUM('svyazkom','sensory_hub','systematics','galaxy') | NULL, к какой компании относится вопрос (если относится) |
| `difficulty` | TINYINT UNSIGNED | NOT NULL, DEFAULT 1; диапазон 1–5 |
| `time_limit_seconds` | INT UNSIGNED | NULL = значение комнаты |
| `is_active` | BOOLEAN | NOT NULL, DEFAULT TRUE |
| `created_at` | DATETIME(3) | NOT NULL |
| `updated_at` | DATETIME(3) | NOT NULL |

`company` — дополнительная характеристика, не категория. При дальнейшем развитии компании тоже можно вынести в отдельную таблицу. **Опубликованные вопросы, уже выбранные для действующих комнат, не редактировать in place**.

### 7.5 `question_options`

| Поле | Тип | Ограничения / назначение |
|---|---|---|
| `id` | BIGINT UNSIGNED | PK |
| `question_id` | BIGINT UNSIGNED | NOT NULL, FK → questions.id |
| `text` | TEXT | NOT NULL |
| `is_correct` | BOOLEAN | NOT NULL, DEFAULT FALSE |
| `sort_order` | SMALLINT UNSIGNED | NOT NULL; порядок кнопок |

Индексы: `(question_id, sort_order)` UNIQUE. При публикации сервер проверяет **не менее 2 вариантов** и **ровно один верный**. В MVP порядок вариантов фиксирован `sort_order`; при необходимости персонального перемешивания добавить поле порядка/снимок вариантов для назначения вопроса.

### 7.6 `room_questions`

| Поле | Тип | Ограничения / назначение |
|---|---|---|
| `id` | BIGINT UNSIGNED | PK |
| `room_id` | BIGINT UNSIGNED | NOT NULL, FK → rooms.id |
| `question_id` | BIGINT UNSIGNED | NOT NULL, FK → questions.id |
| `created_at` | DATETIME(3) | NOT NULL |

Ограничение `UNIQUE(room_id, question_id)`. Количество подходящих вопросов в комнате должно быть **не меньше** `rooms.questions_count`.

### 7.7 `participants`

| Поле | Тип | Ограничения / назначение |
|---|---|---|
| `id` | BIGINT UNSIGNED | PK |
| `room_id` | BIGINT UNSIGNED | NOT NULL, FK → rooms.id |
| `user_id` | BIGINT UNSIGNED | NOT NULL, FK → users.id |
| `status` | ENUM('playing','completed','expired') | NOT NULL, DEFAULT 'playing' |
| `total_score` | INT UNSIGNED | NOT NULL, DEFAULT 0 |
| `current_question_number` | SMALLINT UNSIGNED | NOT NULL, DEFAULT 1; указатель прогресса |
| `joined_at` | DATETIME(3) | NOT NULL |
| `completed_at` | DATETIME(3) | NULL |

**Уникальность:** `UNIQUE(room_id, user_id)`. Индекс для рейтинга: `(room_id, total_score)` (при необходимости дополнить). `total_score` — денормализованный кэш, **изменяется в той же транзакции**, что и вставка единственного ответа. Не доверять клиенту при изменении баллов.

### 7.8 `participant_questions`

| Поле | Тип | Ограничения / назначение |
|---|---|---|
| `id` | BIGINT UNSIGNED | PK |
| `participant_id` | BIGINT UNSIGNED | NOT NULL, FK → participants.id |
| `question_id` | BIGINT UNSIGNED | NOT NULL, FK → questions.id |
| `position` | SMALLINT UNSIGNED | NOT NULL, 1..N |
| `status` | ENUM('pending','active','answered','expired') | NOT NULL, DEFAULT 'pending' |
| `sent_at` | DATETIME(3) | NULL, время успешной выдачи |
| `expires_at` | DATETIME(3) | NULL, дедлайн ответа |
| `telegram_message_id` | BIGINT | NULL, ID Telegram-сообщения |
| `completed_at` | DATETIME(3) | NULL |

Ограничения: `UNIQUE(participant_id, position)` и `UNIQUE(participant_id, question_id)`; индекс `(status, expires_at)` для фонового обработчика. На уровне сервиса + транзакционной блокировки участника гарантируется **не более одного активного задания**. Для надёжной доставки можно расширить статус на `sending` или добавить служебное поле `delivery_state`, чтобы повторный `/start` корректно восстанавливал сбои отправки.

### 7.9 `answers`

| Поле | Тип | Ограничения / назначение |
|---|---|---|
| `id` | BIGINT UNSIGNED | PK |
| `participant_question_id` | BIGINT UNSIGNED | NOT NULL, FK → participant_questions.id, **UNIQUE** |
| `selected_option_id` | BIGINT UNSIGNED | NOT NULL, FK → question_options.id |
| `is_correct` | BOOLEAN | NOT NULL |
| `response_time_ms` | INT UNSIGNED | NOT NULL |
| `points_awarded` | SMALLINT UNSIGNED | NOT NULL |
| `answered_at` | DATETIME(3) | NOT NULL |

**`UNIQUE(participant_question_id)` обеспечивает ровно один сохранённый ответ.** Backend дополнительно проверяет, что `selected_option_id` относится к `question_id` назначенного вопроса. Для просроченного вопроса запись в `answers` не создаётся, статус назначения — `expired`, оценка — 0.

## 8. Обработка ответа: конкурентность и запрет повторной попытки

Критическая операция выполняется в **одной транзакции** MySQL/InnoDB.

1. Получить callback из Telegram и идентифицировать пользователя по `callback_query.from_user.id`.
2. Начать транзакцию и **заблокировать строку участника**, затем строку `participant_questions` через `SELECT ... FOR UPDATE` (единый порядок блокировок для всех операций).
3. Проверить принадлежность вопроса и варианта, состояние `active`, отсутствие ответа, активность комнаты и серверные сроки `now < min(expires_at, rooms.ends_at)`.
4. **Первой бизнес-операцией сохранить выбранный вариант** в `answers` (признак правильности и баллы рассчитываются сервером; сохраняются в этой же транзакции). Это именно фиксация *первого* выбора, без пересдачи.
5. Сравнить с правильным вариантом, рассчитать баллы по времени, заполнить поля результата в `answers`.
6. Перевести назначенный вопрос в `answered`, обновить `participants.total_score += points`.
7. `COMMIT`; только после успешного коммита отредактировать сообщение Telegram с результатом.
8. Если ответ уже существует — **не начислять повторно**, вернуть сохранённый результат. Если вопрос просрочен — закрыть его как `expired` с 0 баллов.

**Атомарность важнее порядка SQL-команд:** при ошибке до коммита вся транзакция откатывается; пользователь не должен получить баллы без ответа и наоборот. Для однозначной фиксации времени использовать единый источник времени сервера/БД; проверять дедлайн после получения блокировки по установленной политике.

Псевдокод:

```python
async def submit_answer(telegram_id, participant_question_id, option_id):
    async with transaction():
        participant = await lock_and_get_participant(telegram_id, participant_question_id)
        assignment = await lock_assignment(participant_question_id)
        assert_room_and_question_active(participant, assignment)
        assert_option_belongs_to_question(option_id, assignment.question_id)
        if assignment.status != "active":
            return await existing_result_or_expiration(assignment)
        result = await record_first_answer_and_score(assignment, option_id)
        await mark_answered_and_add_score(participant, assignment, result)
    return result  # затем обновить сообщение Telegram
```

Защита обеспечивается одновременно транзакциями, блокировками, уникальными индексами и серверной проверкой состояний. Дополнительно бот вызывает `answerCallbackQuery`, чтобы Telegram убрал индикатор загрузки.

## 9. Завершение таймеров и комнат

- Отдельный worker раз в несколько секунд ищет назначения `active` с прошедшим `expires_at` и атомарно переводит их в `expired` (без начисления).
- Затем при возможности редактирует Telegram-сообщение и показывает правильный вариант, объяснение и кнопку «Далее».
- Даже если worker задержался, обработчик ответа **сам проверяет дедлайн**, поэтому поздние ответы не принимаются.
- По `rooms.ends_at` комната закрывается, незавершённые участники получают `expired`, все их оставшиеся вопросы становятся недоступны. В боте отображаются уже накопленные баллы без места в рейтинге.
- Если сообщение не удалось обновить, следующее действие `/start` или `/score` восстанавливает состояние; повторного начисления нет.
- При рестарте сервиса состояние восстанавливается из MySQL; локальные in-memory таймеры не являются источником истины.

## 13. Нефункциональные требования

- **Целостность:** единственный ответ и начисление баллов защищены уникальными индексами и транзакциями.
- **Восстановление:** перезапуск бота/API/worker не приводит к потере прогресса или повторной выдаче уже пройденного вопроса.
- **Безопасность:** проверка Telegram ID из callback, отсутствие правильных ответов в данных кнопок, параметризованные запросы, авторизация админки.
- **Стабильность:** повторные callback, сетевые ошибки, таймауты и двойные клики не меняют уже зафиксированный результат.
- **Скорость:** leaderboard с индексами и без тяжёлого пересчёта каждого ответа на каждом запросе.
- **Публичные данные:** по возможности только никнейм/отображаемое имя, баллы и прогресс; без Telegram ID и приватной информации.
- **Наблюдаемость:** журнал ошибок API/бота, события регистрации, выдачи вопроса, ответа, истечения таймера и закрытия комнаты.

## 15. Что входит в MVP и что можно добавить позднее

**В MVP:** QR-вход, комнаты, категории, банк вопросов с объяснениями и вариантами, 10 персональных неповторяющихся заданий, единственный ответ, таймеры, начисление баллов, Telegram-кнопка «Далее», веб-рейтинг каждые 15 секунд, базовое администрирование, MySQL, Docker Compose.

**Позднее:** расширенная аналитика по компаниям и категориям, экспорт CSV, фирменная анимация топ-3, история мероприятий, генератор QR, несколько экранов рейтинга, настройка распределения категорий/сложности, расширенное версионирование вопросов, дополнительные механики наград.

## 16. Зафиксированные решения

- **БД — MySQL**, не PostgreSQL.
- **WebSocket не используется**: браузер делает HTTP polling **раз в 15 секунд**.
- **Участие только один раз в конкретной комнате** по Telegram ID.
- **У каждого человека своя последовательность из 10 вопросов без повторов внутри набора**.
- **Вопросы идут по одному**; следующий — только после кнопки **«Далее»**.
- **Ответ выбирается inline-кнопкой**; сохраняется первый принятый ответ; пересдач нет.
- **После ответа** показываются верный вариант, **обязательное краткое объяснение** и набранные баллы; варианты кнопок исчезают.
- **Категории — отдельная таблица `categories`**.
- **Место в рейтинге — только на сайте**, не в Telegram-боте.
- Игровая логика единая для бота и сайта; подсчёт баллов и проверка таймеров выполняются исключительно сервером.
